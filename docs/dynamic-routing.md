# Модуль динамической маршрутизации

Модуль назначает домены и IPv4/CIDR разным выходным туннелям на управляемом VPN-сервере. Он заменяет установку тысяч отдельных маршрутов в основной таблице Linux.

## Модель

- **Модуль** относится к одному исходному VPN-серверу и может быть включен или выключен.
- **Направление** связывает правила с существующим выходным интерфейсом, например `awg-egress` или `office1`.
- **Доменное правило** наполняет временный RAM-набор IPv4-адресами из DNS-ответов.
- **CIDR-правило** помещается в постоянный `nftables` set и не зависит от DNS.
- **Приоритет** определяет первое направление при пересечении правил. Меньшее число имеет больший приоритет.

Создание направления не разворачивает межсерверный туннель. Интерфейс и его peer должны уже существовать и иметь рабочее соединение с сервером выхода.

## DNS

`dnsmasq` работает как прозрачный промежуточный resolver. Запросы VPN-клиентов на TCP/UDP 53 перенаправляются к нему, а сам resolver пересылает их настроенным upstream-серверам. Ответ клиенту сохраняет адрес DNS-сервера, к которому обратился клиент.

Форматы доменных правил:

- `youtube.com` — домен и его поддомены;
- `*.youtube.com` — только поддомены;
- `api.youtube.com` — этот DNS suffix;
- `*.com` — запрошенные имена внутри зоны `.com`;
- `*` — все DNS-имена.

Правила соответствуют доменной семантике `dnsmasq`. Модуль обрабатывает A-записи и IPv4. DNS-over-HTTPS и DNS-over-TLS не являются обычными запросами на порт 53 и требуют отдельной политики клиента или firewall.

Модуль автоматически выбирает доступный RAM-backend. При наличии `nftset` адреса добавляются прямо в `nftables`; на Ubuntu 22.04, где пакет `dnsmasq` собран с `ipset no-nftset`, используются kernel `ipset` и совместимая mangle-цепочка. Приоритеты, policy tables и NAT в обоих режимах одинаковы.

## Обработка пакета

1. Клиент отправляет DNS-запрос через WG/AWG.
2. Прозрачное правило направляет запрос локальному `dnsmasq`.
3. IP из подходящего ответа добавляется в RAM-набор соответствующего направления.
4. Пакет клиента к этому IP получает `fwmark`.
5. `ip rule` выбирает отдельную таблицу с default-маршрутом через выходной интерфейс.
6. Исходный адрес маскарадуется адресом выходного туннеля.

Статические CIDR проверяются раньше динамических доменных адресов. Затем для динамических адресов исключаются loopback, RFC1918, link-local, CGNAT, multicast и зарезервированные диапазоны. Частный адрес можно направить явно, добавив CIDR в нужное направление.

## Хранение и восстановление

- Доменные правила и CIDR хранятся в БД панели.
- Полученные из DNS IP находятся только в kernel RAM-наборах (`nftset` или `ipset`) и удаляются по TTL.
- Конфигурация, systemd unit и timer находятся в `/opt/awgcontrolpanel/dynamic-routing`.
- Перед первым переключением peer-конфиги и старые route-файлы сохраняются в закрытом каталоге `backups` на узле.
- Выходной WireGuard/AmneziaWG peer получает `AllowedIPs = 0.0.0.0/0` при `Table = off`; фактический путь определяют только marks и policy tables.

При отключении снимаются DNS-перехват, marks, policy rules, таблицы и RAM-наборы. Peer остается с `Table = off`, поэтому основной маршрут сервера не меняется.

## Требования к узлу

- Linux с `nftables`, `iproute2`, `iptables` и systemd;
- `dnsmasq` с поддержкой `nftset` или `ipset` (backend выбирается автоматически);
- включенный IPv4 forwarding;
- рабочие выходные интерфейсы с одним peer для управляемых WG/AWG-конфигураций;
- доступ исходного сервера к DNS upstream;
- SSH-канал панели с ограниченным административным доступом.

## Проверка после применения

1. `dnsmasq` и `awg-dynamic-routing.timer` активны.
2. `nft list table inet awg_policy` показывает static sets, а выбранный backend записан в `/opt/awgcontrolpanel/dynamic-routing/dns-backend`.
3. DNS-запрос тестового домена увеличивает dynamic set нужного направления.
4. `ip rule` содержит marks из панели, а соответствующие таблицы имеют default через ожидаемый интерфейс.
5. `ip route get <IP> mark <MARK>` выбирает правильный выход.
6. Офисные CIDR, публичные домены, WG и AWG2 проверяются отдельными клиентами.
7. После перезапуска контейнера и сервера правила восстанавливаются systemd timer.
